What is Taskpilot?

Taskpilot is a field operations platform used in the diamond and parcel logistics industry. It connects three types of users — Admin (web panel), Parties (business clients), and Employees (field workers).

The mobile app is used by Employees and Parties. Parties create pickup/delivery requests. Employees receive notifications, accept nearby jobs, go to the party location, collect payments, upload photos, and handle document signing — all from their phone.

Your task is to build a working mini version of this app covering the core request flow.

02

Task Breakdown

T-01

Login Screen — Two Roles

Required

Build a login screen that supports two user roles — Employee and Party. After login, the app should navigate to the correct home screen based on the role.

  • Username + Password fields with basic validation (empty check)
  • Role selector — toggle or dropdown to choose Employee or Party
  • On login, store the role in local state (Provider / Riverpod / Bloc — your choice)
  • Employee → goes to Request List screen
  • Party → goes to Create Request screen
  • No real API needed — use hardcoded mock credentials
  • Show a loading indicator on button tap for at least 1 second before navigating
// Mock credentials to use Employee: username: "emp1" password: "1234" Party: username: "party1" password: "1234"
T-02

Party — Create a Request

Required

When logged in as a Party, they should be able to create a new service request. Request type is always Pick for parties.

  • Form with Party Name (pre-filled from login), Date & Time picker, and optional Note field
  • Request type is fixed as "Pick" — show it as a read-only label
  • On submit, add the request to a local list (in-memory, no backend needed)
  • New request should have status: Pending
  • Show a success snackbar or dialog after submission
  • After submit, show a My Requests list below with the created requests and their status chips
T-03

Employee — Request List & Accept

Required

When logged in as an Employee, show a list of all available requests. Employee can accept a Pending request.

  • Show a list of mock requests (preload at least 3 dummy requests with different statuses)
  • Each list item shows: Party name, Request type, Date/Time, Status chip
  • Status chips with colors — Pending (amber), Accepted (blue), Completed (green)
  • Tap on a Pending request → show Accept button on detail screen
  • On Accept → status updates to Accepted in the list (real-time UI update)
  • Accepted request shows employee name who accepted it
  • Add a filter bar at the top — All / Pending / Accepted / Completed
T-04

Employee — Complete Request with Photo

Required

On an Accepted request, the employee should be able to take or upload a photo and mark it as Complete — simulating the on-site parcel photo capture.

  • On the Request Detail screen, show a "Complete Request" button (only if status = Accepted)
  • On tap — open a bottom sheet or dialog with option to Take Photo or Pick from Gallery
  • Use image_picker package for this
  • Show a preview of the selected image in the bottom sheet
  • On confirm — update status to Completed and display the image thumbnail on the detail screen
  • Show a success message after marking complete
// Suggested packages image_picker: ^1.0.0 # camera + gallery provider: ^6.0.0 # or riverpod — state mgmt intl: ^0.18.0 # date formatting
T-05

Bill View Screen (Bonus)

Bonus

Build a simple Bill screen accessible from the Employee home. This is a bonus task — do it only if T-01 to T-04 are solid.

  • Show a list of mock bills — party name, amount, kasar (balance), status
  • Status options: Pending, Taken, Accepted with colored chips
  • Tap on a bill → show a detail view with collected amount field
  • A "Mark as Taken" button that updates status
  • Bonus extra: Add a Share button that uses the share_plus package to share the bill text to WhatsApp or any app
// Bonus package share_plus: ^7.0.0 # share bill text / simulate WhatsApp send

Technical Requirements

🏗

State Management

Use Provider, Riverpod, or Bloc. No raw setState across screens. We want to see how you manage shared app state.

📁

Folder Structure

Separate screens, models, providers/controllers, and widgets into clean folders. We check project organisation.

🎨

UI Quality

No default Flutter blue. Pick a clean theme. Proper padding, consistent font sizes, status chip colors. It should feel like a real product.

📱

No Backend Required

All data is in-memory / mock. No API calls needed. Focus on the Flutter code, UI, and state — not the backend.

📝

README

Include a README with: how to run the app, what you built, which state management you used, and any known issues.

⚡

Performance

No unnecessary rebuilds. Use const where possible. List screens should use ListView.builder, not Column with children.
